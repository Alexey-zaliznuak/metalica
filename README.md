# Металлика — заказы и правки

Веб-платформа для студии портретов на металле. Заменяет хаос из двух чатов ВК
(«заявки» и «правки») структурированными тредами по заказам — как мессенджер,
где переписываются менеджеры и художники эскизов и правок. Вся переписка хранится, поэтому метрики
(сколько правок в заказе и сколько времени они занимали) считаются автоматически.

## Стек

- **Бэкенд:** NestJS + Prisma + PostgreSQL
- **Фронтенд:** Vite + React + TypeScript + MUI (Material UI)
- **Хранилище файлов:** MinIO (S3-совместимое)
- **Инфраструктура:** docker-compose + nginx (внутренний reverse-proxy)

## Архитектура

```
браузер → HTTPS → [внешний nginx] → [docker nginx :3000] ┬→ /          → frontend
                                                         ├→ /api       → backend → PostgreSQL
                                                         ├→ /socket.io → backend
                                                         └→ /files     → MinIO
```

Файлы читаются без presigned-подписи по постоянным URL вида
`https://metallity-crm.ru/files/<s3-key>`. Бакет разрешает анонимный
`s3:GetObject`, но загрузка и удаление по-прежнему выполняются только backend с
учётными данными MinIO.

### Превью вложений

При загрузке растрового изображения backend сохраняет оригинал и две WebP-копии:
миниатюру до 600 px и версию для просмотра до 1800 px по длинной стороне.
В чатах и производственных вложениях загружается миниатюра; по клику — версия
для просмотра. «Открыть оригинал», скачивание и подготовка файла для производства
используют исходный файл. Вес файла на карточке относится к оригиналу.

У фото в чате заказа и среди прикреплённых для производства кнопка «Установить размер» раскрывает варианты
30 х 40, 40 х 60 и 60 х 80. Выбранный размер хранится в `Attachment.photoSize`
и отображается над весом файла, в том числе после повторного открытия заказа.
Для окружений с миграциями добавлена `20261015120000_attachment_photo_size`;
Docker-запуск применяет изменение схемы через существующий `prisma db push`.

Обработка выполняется в отдельных worker threads, по умолчанию до четырёх изображений одновременно на процесс, с лимитом
100 млн пикселей и 60 секунд на задание. HEIC/HEIF декодируются на сервере;
PDF и DNG сохраняют прежние карточки файлов. Ошибка превью не отменяет загрузку
оригинала и не заставляет браузер автоматически скачивать его для миниатюры.

После обновления схемы и запуска backend старые вложения автоматически
обрабатываются в фоне с пополнением свободных мест очереди каждую секунду. До готовности
показывается заглушка; готовые превью видны при повторной загрузке заказа/чата.
Ошибки хранилища повторяются до трёх попыток и логируются. При устранении причины
вложения со статусом `failed` можно вернуть в очередь:

```sql
UPDATE "Attachment" SET "previewStatus" = 'pending', "previewAttempts" = 0
WHERE "previewStatus" = 'failed';
```

Docker-запуск обновляет схему через существующий `prisma db push`. Для окружений
с миграциями добавлены `20261009120000_attachment_previews` и
`20261009130000_production_files`.

### Файлы для производства

Производственные файлы готовятся только для вложений из раздела «Фото для печати»
заказа. Обычные фото чата и закреплённые эскизы не получают производственные
варианты, пока их не прикрепят в этот раздел. Проверка действует и для прямых
запросов API, и перед скачиванием исходника фоновой задачей: старое задание для
фото вне раздела удаляется без конвертации. Обычные превью чата работают отдельно.

При прикреплении фото для производства backend сразу ставит в очередь PostgreSQL
все три размера текста: 30×40, 40×60 и 60×80,
начиная с выбранного пользователем размера. Недостающие задания для ранее
прикреплённых фото добавляются автоматически при запуске и фоновых проверках.
Уже готовые актуальные версии переиспользуются. В фоне backend скачивает
оригинал, добавляет шапку в worker thread и сохраняет готовый
PNG в MinIO. Превью и производственные файлы используют общий лимит, который
настраивается в `.env` (по умолчанию четыре обработки одновременно на процесс). Кнопка проверяет состояние
каждые четыре секунды; нажатие до завершения показывает уведомление. Готовый
файл скачивается из кеша. После ошибки доступны три автоматические попытки
и кнопка повторной подготовки.

Пока основной статус — «Готовится», рядом доступна кнопка «Скачать досрочно».
Она поднимает в начало очереди только это фото в выбранном размере и автоматически
скачивает PNG после готовности, пока карточка открыта. Уже работающие задачи завершаются;
срочная подготовка занимает ближайшее свободное место с соблюдением лимитов.
Приоритет хранится в БД и сохраняется после перезапуска backend. Повторное нажатие
не создаёт дополнительную версию того же файла.

Параметры параллельной обработки в `.env`:

- `IMAGE_JOB_CONCURRENCY=4` — общий максимум одновременно выполняемых операций с изображениями.
- `IMAGE_PREVIEW_CONCURRENCY=4` — максимум операций превью, включая новые загрузки и фоновую обработку.
- `PRODUCTION_IMAGE_CONCURRENCY=4` — максимум подготовки файлов для производства.
- `UV_THREADPOOL_SIZE=16` — размер общего пула native-операций Node.js/Sharp,
  начальное значение для сервера с 16 доступными CPU; по умолчанию Node.js использует 4.

Лимиты отдельных типов ограничены общим максимумом. Например, при общем лимите 4
и лимите превью 2 производство может занять оставшиеся места. Все значения — положительные
целые числа, лимиты действуют на один backend-процесс. После изменения `.env`
пересоздайте backend-контейнер: `docker compose up -d --force-recreate backend`.

Количество заданий очереди и число одновременно выполняемых native-операций —
разные ограничения. Даже 30 заданий могут ждать один общий пул libuv из четырёх
потоков; создание worker threads не создаёт отдельный пул для каждого задания.
В используемой сборке `node:20-slim` Sharp на glibc без jemalloc по умолчанию
использует один поток libvips на изображение. Поэтому рост лимитов очереди
сам по себе не гарантирует рост загрузки CPU.

Для сервера с 16 доступными CPU и лимитами очереди 35/15/30 начните с
`UV_THREADPOOL_SIZE=16`. Docker Compose уже передаёт корневой `.env` через
`env_file`, поэтому пересборка образа для этой настройки не нужна — нужен
именно пересозданный контейнер. Переменная должна быть задана до старта Node.js:
её загрузка через dotenv внутри уже работающего процесса не гарантирует изменения
пула. При локальном запуске экспортируйте её в оболочке до `npm run start:dev`.

Проверка конфигурации внутри контейнера (выводятся только настройки CPU):

```bash
docker compose exec backend node -e 'console.log({cpu:require("os").availableParallelism(),uvThreadpoolSize:process.env.UV_THREADPOOL_SIZE||"4 (default)",sharpThreadsPerImage:require("sharp").concurrency()})'
```

После изменения сравнивайте темп готовых файлов и среднюю длительность в
«Очереди изображений». Нагрузка может оставаться ниже 100%, если задачи ждут
MinIO, диск или память. Документация: [параллелизм Sharp](https://sharp.pixelplumbing.com/performance/),
[общий пул libuv](https://docs.libuv.org/en/v1.x/threadpool.html).

В «API-метрики» добавлена вкладка «Очередь изображений»: отдельные графики очереди
превью и производства, текущие количества ожидающих и выполняемых задач, ошибки,
скорость и приблизительное время освобождения очереди при отсутствии новых задач.
Производство считается отдельно для каждого размера, превью — по уникальным исходникам.
«Готово вариантов за последний час» включает обработку ранее прикреплённых фото
и обновление файлов после изменения шапки, а не только новые загрузки за этот час.
Прогноз появляется после успешных обработок; при недостатке данных время не выдумывается.
Замеры сохраняются каждые 20 секунд и хранятся 7 дней; интерфейс обновляется каждые
10 секунд. Для окружений с миграциями перед запуском обновлённого backend примените
`20261013110000_image_queue_metrics` и `20261013120000_production_priority`
командой `npm run prisma:migrate` в `backend`. Docker-запуск обновляет схему через
существующий `prisma db push`.

Подраздел **«API-метрики» → «Дебаг производства»** (`/dev-metrics?tab=production-debug`)
показывает постановки за последние 60 минут по каждому заказу: новые задачи,
фото по уникальным ID, три размера и повторную подготовку. Строка заказа
раскрывается до отдельных фото. Например, 12 новых задач для 4 фото дают четыре
полных набора по три размера; неполные/повторяющиеся наборы видны отдельно.
Изменение данных для печати и ручной повтор после ошибки не смешиваются с новыми
задачами. Автоматические попытки воркера и чтение кеша не увеличивают счётчик.
Журнал пишется в одной транзакции с постановкой задания, переживает удаление
фото/заказа и хранится 7 дней. События до выкладки не восстанавливаются.
Для установки через миграции примените `20261021140000_production_task_events`;
Docker-запуск создаёт таблицу через существующий `prisma db push`.
API: `GET /api/dev-metrics/production-debug`, ADMIN или право `API_METRICS_VIEW`. Вкладка обновляется
каждые 10 секунд, чтение статистики не запускает обработку изображений.

Доступ ко всем вкладкам `/dev-metrics` можно выдать отдельно: **«Пользователи» →
«Редактировать» → «Дополнительные права» → «Просмотр API-метрик»**.
Право `API_METRICS_VIEW` открывает API BlueSales, очередь изображений, дебаг
производства и просмотр состояния Inbound-синка. Менять режим синка и выдавать
права может только ADMIN. Обычный `METRICS_VIEW` не даёт доступа к API-метрикам.
После выдачи права менеджеру нужно обновить страницу; сервер проверяет актуальные
права в БД при каждом запросе, включая отзыв доступа у уже вошедшего пользователя.
Для окружений с миграциями примените `20261021150000_api_metrics_view_scope`;
Docker-запуск добавляет значение в enum через существующий `prisma db push`.

Каждый размер текста имеет отдельную версию. Изменение номера,
артикулов, комментария или службы доставки обновляет шапку; устаревший файл
удаляется. В шапке производственных вложений печатается `номер-заказа-номер-фото`,
например `123-1`: фото нумеруются с единицы в порядке списка вложений (ID по
возрастанию). При удалении фото последующие версии обновляются с новой нумерацией.
Старые производственные фото автоматически попадают в очередь после
запуска. PNG использует адаптивную фильтрацию и сжатие уровня 6 без потери качества;
RGB-исходники не получают лишний канал прозрачности, разрешение и DPI сохраняются.

Удаление фото, снятие закрепления эскиза и удаление заказа ставят подготовленные
версии в надёжную очередь удаления. Ошибки MinIO повторяются с задержкой. Поздний
результат уже удалённого фото также очищается; незавершённые задания после
перезапуска восстанавливаются по истечении десятиминутной аренды. Очередь удаления
не затрагивает исходник, который может использоваться в чате.

Каждые 10 секунд `ImageJobsLogService` пишет в лог количества превью и
производственных файлов по статусам в БД, включая нулевые значения, а также
ожидающие и выполняющиеся операции общей очереди текущего процесса. Для превью
считаются уникальные исходники в каждом статусе; `pending` включает обработку.
Производство считается отдельно для каждого размера текста. Локальные операции
включают новые загрузки до создания вложения и проверку очереди производства.

Проверки: в `backend` — `npm run build`, затем
`node --test test/image-job-config.test.cjs test/image-queue-metrics.test.cjs test/production-task-metrics.test.cjs test/image-previews.test.cjs test/production-image.test.cjs test/production-files.test.cjs test/order-assets.test.cjs`;
в `frontend` — `npm run build` и `node --test test/image-previews.test.cjs test/production-download.test.cjs`.
Для проверки HEIC задайте `HEIC_TEST_FILE` с путём к тестовому HEIC-файлу.

## Модель данных и метрики

Вся переписка — это `Message` в треде заказа. У сообщения есть тип `kind`:

- `NORMAL` — обычное сообщение
- `REVISION_REQUEST` — запрос на правку (старт таймера)
- `REVISION_ANSWER` — исправленный вариант (стоп таймера)

Ответ автоматически привязывается к последнему открытому запросу правки
(`answerToId`, self-relation). Отсюда метрики:

- **правок на заказ** = число `REVISION_REQUEST`
- **время правки** = `answer.createdAt − request.createdAt`
- **открытые/зависшие правки** = запросы без ответа (дольше N часов)

## Запуск

1. Скопируйте переменные окружения и при желании поправьте:

   ```bash
   cp .env.example .env
   ```

   Для продакшена обязательно смените `JWT_SECRET`, пароли и задайте:

   ```env
   APP_DOMAIN=metallity-crm.ru
   APP_PROTOCOL=https
   APP_PORT=3000
   ```

   `APP_DOMAIN` указывается без протокола. Backend использует его во всех
   публичных ссылках на файлы. Для локального HTTP-запуска задайте
   `APP_DOMAIN=localhost:8080` и `APP_PROTOCOL=http`.

2. Поднимите всё:

   ```bash
   docker compose up -d --build
   ```

   При старте бэкенд сам накатит схему БД (`prisma db push`) и заполнит
   демо-пользователей и демо-заказ.

3. Откройте приложение: <http://localhost:3000>
   - Консоль MinIO: <http://localhost:9001>

## Временное отключение импорта из BlueSales

Если BlueSales недоступен и менеджеры меняют статусы в CRM, администратор может
открыть **«API-метрики» → «Inbound-синк · BlueSales → сайт»** и выключить импорт.
Изменение применяется сразу, без перезапуска backend. Выбранный режим хранится
в БД и сохраняется после рестартов. При первом запуске настройка включена.
Переменная `BLUESALES_INBOUND_SYNC_ENABLED` больше не используется — удалите её
из окружения развёртывания. Остальные параметры интеграции остаются в env.

Настройка доступна только администратору: `GET /api/dev-metrics/inbound-sync`
возвращает `{ enabled, updatedAt }`, `PATCH` по тому же адресу принимает
`{ "enabled": false }` или `{ "enabled": true }`. Backend работает в одной
реплике; все пути импорта используют общий экземпляр настройки.

Переключатель блокирует все пути импорта: cron заказов и лидов, оба refresh-loop,
полный импорт при старте, добор пропущенных записей и ручное обновление карточки.
Прямые `upsertOrder` / `upsertLead` и обновления справочников источников, каналов
продаж и тегов также защищены. Заказы, лиды, статусы, менеджеры, суммы, комментарии,
теги и `rawPayload` из БС не записываются в CRM. Фоновые запросы импорта блокируются
и после ожидания в очереди API; отключённый полный импорт не запускается даже
при `BLUESALES_FULL_SYNC=true`.

Локальные изменения менеджеров и исходящая очередь статусов продолжают работать.
Проверка доставки статуса читает БС, но при отключённом импорте только подтверждает
задачу очереди, не перезаписывая карточку данными ответа. Диагностические запросы
и проверка существования заказа перед удалением остаются доступны: они ничего
не импортируют. `BLUESALES_ENABLED` менять для этого режима не требуется.

Включайте Inbound-синк после доставки накопленных локальных статусов в БС: после
включения импорта БС снова станет источником входящих обновлений. Фоновые циклы
возобновятся автоматически с учётом расписания, даже если backend был запущен
с выключенным импортом.

Проверка: в `backend` выполните `npm run build`, затем
`node --test test/bluesales-sync-settings.test.cjs test/bluesales-inbound-sync.test.cjs test/bluesales-sync.test.cjs test/order-status-outbox.test.cjs`.

## Внешний HTTPS nginx

TLS завершается только во внешнем nginx. Он должен проксировать весь домен на
docker nginx и передавать WebSocket и исходный протокол.
Порты приложения и MinIO в `docker-compose.yml` привязаны к `127.0.0.1`, поэтому
обойти HTTPS прямым запросом к серверу снаружи нельзя.

Пример внешнего конфига:

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    '' close;
}

server {
    listen 80;
    server_name metallity-crm.ru;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name metallity-crm.ru;

    ssl_certificate /etc/letsencrypt/live/metallity-crm.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/metallity-crm.ru/privkey.pem;

    client_max_body_size 1100m;
    client_body_timeout 3600s;
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_request_buffering off;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
    }
}
```

Не добавляйте HTTPS-редирект во внутренний docker nginx: upstream-соединение
между двумя nginx остаётся HTTP. После изменения конфигурации проверьте её через
`nginx -t` и перезагрузите внешний nginx.

## Локальная разработка (без Docker)

Бэкенд:

```bash
cd backend
npm install
npx prisma generate
# поднимите Postgres и MinIO (можно через docker compose up postgres minio)
npx prisma db push
npm run seed
npm run start:dev
```

Фронтенд:

```bash
cd frontend
npm install
npm run dev   # dev-сервер проксирует /api на http://localhost:3000
```

## Дальнейшие шаги

- Заменить `prisma db push` на полноценные миграции (`prisma migrate`).
- Интеграция с CRM **Bluesales**: автоподтягивание списка заказов (когда будет
  доступ к API), чтобы не вводить номер заказа руками.
- Realtime-обновление тредов (WebSocket) вместо опроса.
