# База без истории Prisma: обновление без reset

Это вспомогательная инструкция только для базы с подтверждённым отсутствием истории. В актуальной локальной БД таблица `public._prisma_migrations` есть, и baseline для неё не нужен. Через предоставленное ограниченное подключение история была недоступна; это не доказывает её отсутствия в рабочей БД. Если отсутствие действительно подтверждено владельцем базы, обычный `prisma migrate deploy` на непустой базе без истории завершится P3005.

Скрипт `baseline-existing-database.js` предназначен только для такой базы. Он **не применяет старые SQL-миграции и не меняет прикладные таблицы**. Сначала проверяет полное совпадение существующей структуры с исходной схемой, затем при явном `--apply` регистрирует уже существовавшие 46 миграций через `prisma migrate resolve --applied`. Новые миграции применяются отдельным шагом.

Перед развёртыванием остановите запись приложения и фоновые процессы и сделайте резервную копию. Используйте тот же checkout миграций для baseline и дальнейшего deploy. Скрипту нужна Git-история с коммитом `71364e7050cf3be0567091c34b3e6850e3494e3e` — это зафиксированная исходная схема, а не текущий HEAD. При shallow clone заранее получите этот коммит.

Из каталога `backend`, с явно заданной переменной `DATABASE_URL` нужной базы (скрипт сам не читает `.env`):

```text
node scripts/baseline-existing-database.js
node scripts/baseline-existing-database.js --apply
npx prisma migrate deploy
npx prisma generate
npm run build
```

Первый вызов только проверяет. При различиях схемы, изменённых старых миграциях или уже существующей непустой истории скрипт останавливается **до записи baseline**. Не обходите такую остановку reset-командами: сначала выясните расхождение. Если история Prisma уже есть, baseline не нужен — используйте обычный deploy после проверки `prisma migrate status`.

Регистрация истории состоит из отдельных `migrate resolve`. Если процесс оборвался, скрипт намеренно не продолжает автоматически: проверьте уже зарегистрированные имена и вручную завершите регистрацию оставшихся старых миграций, только после повторной проверки исходной схемы. Не отмечайте новые миграции применёнными: их SQL ещё должен выполниться.

Исторические SQL-файлы не переписываются; Prisma записывает их фактические контрольные суммы. Проверка совпадения с Git допускает только отличие CRLF/LF, возникающее при checkout на Windows.

Новая миграция правок сохраняет существующие ID, даты открытия и закрытия, активные запросы и связи с историческими сообщениями. Новые циклы уже не привязаны к сообщениям. До включения приложения дождитесь успешного окончания всех новых миграций.

Проверка выполнена только на локальном PostgreSQL: восстановлена копия структуры продакшена без истории миграций, выполнены baseline и deploy. На продакшене эти команды автоматически не запускались.

Дополнительно проверен штатный путь на полном дампе локальной БД `localhost:5435/metalica`, восстановленном в отдельную тестовую базу: история содержала 38 миграций; обычный `migrate deploy` успешно применил восемь ранее ожидавших миграций и две новые. Все прежние записи истории и контрольные суммы остались неизменными. Итоговые `migrate status` и сравнение со схемой Prisma подтверждают соответствие. SQL-проверки открытия, закрытия и сохранения правок прошли; исходная локальная БД не изменялась.
